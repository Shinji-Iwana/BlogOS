# ブログ別の定義：si-note（IT技術ブログ）

**si-note バージョン:** 2.1.0
**適用する共通基準:** 1.0.0 以上
**最終更新日:** 2026-10-07

BlogOSで `blogs.quality_profile = si-note` のブログに適用する。共通基準（`resources/quality/common/`）を前提とし、本フォルダの定義で具体化・追加する。

---

## 1. ブログの目的

IT初心者や、その技術を初めて学ぶ人が、迷わず・挫折せず・実務で活用できるレベルまで体系的に学べる技術ブログを目指す。

対象の技術は特定の分野に限定せず、JavaScript、AWS、Python、Java、Excel、Salesforceなど、ITに関する幅広い技術を扱う。

単なる情報提供ではなく、「初めて学ぶ人でも、このブログだけで理解できる」状態を最終目標とする。ブログ全体を一つの教材として設計する。

## 2. コンセプト

* **初心者第一**：技術力を誇示するのではなく、これから学び始める人を基準に書く。
* **理解重視**：暗記ではなく、「なぜそうなるのか」という本質的な理解を目指す。
* **実践重視**：実際に試せるコード・操作手順・画面例を載せ、読者がその場で再現できるようにする。
* **体系的な学習**：ロードマップと関連記事で、「次に何を学ぶべきか」が自然に分かるようにする。
* **読者満足度最優先**：SEOのテクニックより、読者の疑問・課題を最後まで解決することを優先する。
* **長期価値**：数年後でも価値がある記事を目指す。

## 3. 想定読者

共通基準の「想定読者」は、本節の読者を指す。

### 3-1. メインの読者

* IT初心者。**ITに触れたことがない人**（プログラミングやITの用語を学んだことがない人）を含む
* 初めてその技術に触れる人
* 独学で学習している人
* エラーや疑問を検索している人
* 実務経験が少ない人
* 他の技術の経験はあるが、新しい分野を学び始める人（例：Javaの経験者がAWSを学び始める）

### 3-2. サブの読者

新人エンジニア、学生、社会人の学び直し、資格の取得を目指す人、実務で新しい技術を担当することになった人。

### 3-3. 主な対象外

上級者向けの内部実装や理論だけを求める人、仕様書レベルの詳細だけを求める人、高度な最適化だけを目的とする人。

### 3-4. 書くときの前提

文章は、**ITに触れたことがない人**が読んで理解できるかを基準に書く。その技術の初心者（他の技術の経験がある人を含む）は、この基準で書けば理解できる。

読者は、専門用語を知らない、エラーの経験が少ない、コードを読むことに慣れていない、操作手順に迷いやすい、抽象的な説明だけでは理解しづらい、と考える。そのため、図解・コード例・画面例・操作手順・具体例・例え話を積極的に使う。

判断に迷った場合は、「ITに触れたことがない人が理解しやすいか」を基準にする（共通基準の優先順位「読者の理解」に相当する）。

### 3-5. 用語の説明（このブログで最も重要な基準）

ITに触れたことがない人が記事を理解できない一番の原因は、聞き覚えのない用語（カタカナの用語・英字の略語）が説明なしに出てくることである。そのため、共通基準（`common/writing.md` 2-1「専門用語は、初めて出てくる箇所で説明する。略語は正式名称を併記する」）を、次のとおり具体化する。

* **説明の対象**：**その記事の本文に実際に出てくる語**のうち、ITに触れたことがない人が、意味を自分の言葉で言えない語は、すべて説明する。本文に出てこない語（関連する語・先回りの説明）は説明しない（読者が「本文のどこにもない語の補足がある」と混乱するため）。特に、次の語は必ず説明する。
  * カタカナの用語（例：インタプリタ、コンパイル、フレームワーク、ライブラリ、ブラウザ、サーバー、エンジン、モーダル、アニメーション）
  * 英字の略語・英単語のままの用語（例：Ajax、SPA、API、DOM、HTML、CSS、URL、JSON、Node.js、React）。略語は、正式名称と、その意味を書く
  * 漢字の専門用語（例：非同期処理、変数、関数、引数、戻り値、構文、実行環境）
* **説明しなくてよい語**：日常で使われ、ITに触れたことがない人でも意味を言える語（例：パソコン、スマホ、インターネット、ホームページ、メール、アプリ、ボタン、画面、クリック、ダウンロード）。迷ったら説明する。
* **説明の位置**：その記事で初めて出てくる箇所の直後（`html-rules.md` 3-4 の補足の枠）。見出し・「この記事で分かること」に初めて出てくる語は、本文で最初に出てくる箇所で説明する。
* **記事ごとに説明する**：読者は検索から直接その記事に来るため、ほかの記事で説明した語でも、記事ごとに説明する。用語解説の記事がある語は、あわせてリンクする。
* **説明の書き方**：ITに触れたことがない人が読んで分かる、日常の言葉で1〜2文にし、必要なら例え話を添える。**専門用語を別の専門用語で言い換えない**（例：×「HTTP 通信でサーバーと非同期にデータをやり取りする技術」→ ○「ページを開き直さずに、裏側でインターネットの向こう側のコンピューターと情報をやり取りする仕組み」）。説明の中に専門用語をやむを得ず使う場合は、本文で説明している語だけにする。
* **用語を続けて出さない**：1つの文に、説明が必要な用語を3つ以上詰め込まない。用語が多い箇所は、文を分けるか、先に図・例で全体像を示す。
* その語そのものを解説する記事（例：「DOMとは？」の記事）では、本文の説明を補足の枠の代わりにしてよい。

## 4. 採点項目の適用

* 共通基準 `scoring.md` の採点項目は、ブログ単位では**すべて対象**とする。記事種類ごとの対象外は `article-types.md` 6-1 で定める。
* コード例・画面例・実行結果は、記事の型の項目（`article-types.md` 6章。例：Do の `type.do_code`・`type.do_result`）で判定する。技術記事では原則として必須の観点として扱う。
* `reader.terms`（専門用語の説明）は、3-5 の基準で判定する。説明のない用語が1つでもあれば ○ にしない。
* 必須条件 `req.verified`（コード・手順の動作確認）と `req.not_orphan`（孤立記事でない）は、**対象**とする。

## 5. 記事種類・テンプレート・サイト構造

* 記事種類とテンプレート：`article-types.md`
* サイト構造・ロードマップ・内部リンク：`site-design.md`
* 図解・コード例・エラー解説など技術記事の基準と、収益導線の詳細：`tech-content.md`
* HTMLのルール（記事の並び・部品・広告の位置）：`html-rules.md`

## 6. KPIの確認指標

| 分類 | 確認指標（参考） |
| --- | --- |
| 記事品質 | 全記事の人が確定した点数が95点以上であること |
| 読者満足度 | 滞在時間、スクロール率、コメント・問い合わせ、検索クエリとの一致 |
| SEO | 検索順位、CTR、表示回数、自然検索の流入数、インデックスの状況 |
| サイト内の回遊 | 内部リンクのクリック率、ページ／セッション、回遊率、直帰率 |
| 収益 | 広告のクリック率、アフィリエイトのCVR、記事別の収益、RPM、収益記事への遷移率 |

これらの指標は、BlogOSのGoogle連携（GA4・Search Console・AdSense）で記事単位に確認する。

## 7. 最終確認の問い

公開・更新の前に、次の3つにすべて「はい」と答えられることを確認する。

1. この記事は、IT初心者が追加の検索をせずに理解でき、実際に試しながら学べる内容になっているか。
2. 競合の上位記事と比べて品質で劣らず、一部では明確に上回っているか。
3. 読者満足度・SEO・UX・回遊・収益をバランスよく満たし、95点以上を達成しているか。

## 8. 運営の理念

このブログが目指すのは、検索順位が高い記事、文字数が多い記事、収益だけを目的とした記事ではない。IT初心者が迷わず学び、理解し、実際に試し、実務で活用できるレベルまで成長できる教材を目指す。
