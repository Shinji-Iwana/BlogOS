# 共通基準：BlogOSのAI機能の実行ルールと品質改善の運用

**共通基準バージョン:** 1.0.0
**最終更新日:** 2026-09-24

本ファイルは、BlogOSのAI機能（および人）が、この品質基準を使って記事を評価・作成・改修するときのルールを定める。AIに許可する操作の範囲（WordPressへの反映は人が承認する等）は `docs/BLOGOS_ARCHITECTURE.md` 18章で定義する。

---

## 1. AIの役割

AIは、品質基準に基づく**記事の編集者の補助**として動作する。AIは次を行う。

* 品質基準に従って記事を評価する
* 不足点を洗い出す
* 改善案を示す
* 指定された改修範囲（3章）で、記事の構成・本文の案を作る

AIの出力は案であり、採用するかどうか、公開するかどうかは人が判断する。

## 2. 実行の回数

* 1回の指示につき、AIの実行は1回とする。AIが自分で「95点になるまで」繰り返すことはしない（D-07-03）。
* AIは、出力と一緒に自己評価（`scoring.md` の採点と、残っている不足点）を示す。
* 人は、AIの点数を見て、受け入れるか判断する（受け入れの目安はBlogOSの設定値。初期値90点）。
  * 受け入れる場合：人が直すか、不足点だけを直すようAIに再度指示する。
  * 受け入れない場合：作り直しを指示するか、破棄する。
* 最終的な合格判定（必須条件と95点以上）は、人が確定する。

## 3. 改修範囲

既存記事の改修では、実行のたびに改修範囲を指定する（D-06-01）。指定がない場合は「軽微な改善」とする。

| 改修範囲 | 内容 | 許可されること |
| --- | --- | --- |
| 軽微な改善（既定） | 不足している項目の追加と、表現の改善 | 見出しの構成は維持する。既存の内容を不要に削除しない |
| 構成の見直し | 見出しの構成を含む改善 | 見出しの追加・削除・順序の変更、説明の順序の変更。主要な内容は維持する |
| 全面改修 | 記事の全面的な書き直し | 構成・文章・図解・見出しを全面的に見直す。**人が指定した場合だけ行う** |

どの改修範囲でも、誤った情報は必ず修正し、残さない。表現だけを直して品質不足を放置しない。

## 4. 推測の禁止

AIは、根拠を確認できない情報を推測で補わない。特に、仕様、バージョン、動作の結果、エラーの内容、性能、セキュリティ、推奨する方法、実務経験、数値、比較の結果を推測で書かない。

情報が足りない場合は、次のいずれかで対応する。

* 「情報不足のため確認が必要」と明記する
* 公式情報の参照を促す
* 実際に検証することを前提として書き、検証が必要な箇所を示す
* 記事への追記を提案する

「実際に試した」「実務で使っている」など、AIが経験していないことを事実として書かない。実体験・検証の内容は、人が提供したものだけを使う。

## 5. 実行モード

各モードの具体的な入力と出力の形式は、AI実行テンプレート（`resources/ai/templates/`。未作成）で定める（D-06-07）。

| 実行モード | 目的 | 主な出力 |
| --- | --- | --- |
| SEO分析 | SEOの観点での分析 | 検索意図、競合との差分（人が提供した情報に基づく）、改善提案 |
| 構成作成 | 記事の設計（本文は書かない） | タイトル、検索意図、H2・H3の構成、図・表・例の配置、内部リンク、FAQ、CTAの位置 |
| 品質診断 | 記事の評価 | 採点、必須条件の判定、不足点、改善の優先順位、改善後に期待できる効果 |
| 記事改修 | 既存記事の改善 | 指定された改修範囲での改修案 |
| 新規記事作成 | 新しい記事の作成 | 記事種類とテンプレートに沿った本文の案 |
| HTML出力 | 公開用のHTMLの作成 | ブログ別のHTMLのルールに沿ったHTML |

複数のモードを続けて使う場合は、次の順を推奨する（D-06-06）。

SEO分析 → 構成作成 → 品質診断 → 記事改修 または 新規記事作成 → HTML出力

既存記事の改修では、原則として品質診断を先に行う。

### 5-1. 新規記事作成の手順

1. 検索意図を分析する
2. 想定読者を整理する
3. 記事種類を判定する（ブログ別の定義）
4. 記事種類のテンプレートを選ぶ
5. H2・H3の構成を作る
6. 本文を作る
7. 図解・例・FAQ等を加える
8. SEO・UX・収益導線を確認する
9. 自己評価を示す

テンプレートを機械的に埋めることを目的にしない。

### 5-2. 記事改修の手順

1. 現在の記事を分析する
2. 自己評価（採点）する
3. 不足項目を洗い出す
4. 指定された改修範囲の中で改修方針を決める
5. 改修案を作る
6. 改修後の自己評価を示す

## 6. AIが出力前に確認すること

* 推測・根拠のない断定を含んでいない
* 指定された改修範囲を守っている
* 品質基準（共通基準とブログ別の定義）に従っている
* 要人間確認の項目を、AIの判定に含めていない
* 必須条件の判定と、残っている不足点を示している

## 7. 品質改善の運用

### 7-1. 改善サイクル

記事は公開した時点で完成ではない。次のサイクルで継続的に改善する。

* Plan：品質基準に基づき、検索意図と想定読者を整理して記事を設計する
* Do：記事を作成・改修する
* Check：品質を評価し、KPI・読者の行動を確認する
* Act：不足点を改善し、合格基準を満たすまで修正する

### 7-2. 見直しのタイミング

* 定期：公開後、3か月・6か月・12か月を目安に見直す。
* 臨時：検索エンジンのアップデート、技術・製品の仕様変更、UIの変更、ライブラリの更新、新しい推奨方法、セキュリティ上の更新があった場合。
* 競合の再調査：順位が下がった、CTRが下がった、検索意図が変化した場合。

### 7-3. 改善の優先順位

| 優先度 | 内容 |
| --- | --- |
| 最優先 | 誤った情報・仕様の変更 |
| 高 | 検索意図の不足、想定読者向けの説明の不足 |
| 中 | 網羅性、SEO、UX、回遊の改善 |
| 低 | 収益、デザインの改善 |

### 7-4. ブログ全体の見直し

記事単体ではなくブログ全体を定期的に見直す。対象：記事の構造（ロードマップ等）、カテゴリの構成、内部リンク、収益導線、重複記事・カニバリゼーション、孤立記事。

### 7-5. 品質基準の更新

次の場合は、品質基準そのものを更新する。検索エンジンのアルゴリズムの変更、SEOの傾向の変化、技術仕様の変更、AIの性能の向上、新しい記事種類の追加、新しい基準の追加。

更新時は、基本原則との整合性と、他のファイルとの整合性を確認し、バージョンと変更履歴を更新する（`README.md` 4章）。
