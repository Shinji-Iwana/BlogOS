# 品質基準 2.0.0 の案（確認用）

**状態：** 確定（2026-10-03。利用者が推奨案で了承し、`resources/quality/` に反映した。以後の正本は `resources/quality/`。本書は経緯の記録）
**対象：** 共通基準 `common/scoring.md` 1.3.0 → 2.0.0、si-note `article-types.md`・`profile.md` 1.4.0 → 2.0.0
**決定：** D-47（評価の作り直し。確定したら記録する）

本書は、今の品質基準（`resources/quality/`）をどう変えるかの案である。確定するまで、BlogOS の品質診断・記事改修は今の基準（1.3.0／1.4.0）で動く。

---

## 1. 何を変えるか（要点）

| # | 変えること | 理由 |
| --- | --- | --- |
| 1 | 評価を4層にする：①公開の条件 ②総合品質（100点） ③観点ごとの適合度（%） ④実績（点数にしない） | 合計点だけでは、何に強く何に弱いかが分からない |
| 2 | 採点項目を、確かめられる単位に分け、**項目ごとに ○・△ の判定の基準を文章で決める** | 「SEO 10点」のように大きな項目では、何がどう悪いかを示せず、改修で直ったかも確かめられない |
| 3 | **記事の型（Know・Do・Solve・Compare・実践・ロードマップ・収益記事）ごとの採点項目**（15点）を新しく作る。型の★の項目が × なら合格にしない | 記事の型によって「良い記事の形」が違うのに、今は採点に入っていない |
| 4 | 検索結果で選ばれるか（タイトル・メタディスクリプション）と、収益化の項目を独立させる | クリック率と収益に直結する項目が、合わせて5点しかない |
| 5 | 1つの判定を、関係する観点に集計する（観点ごとに別々に採点しない） | 同じ項目を何度も採点すると、同じ改善点が何重にも数えられる |
| 6 | 品質診断は、○ でない項目ごとに「どこが・何が・どう直すか」の**指摘**を出し、記事改修はその指摘ごとの**対応**を出し、改修後の診断で指摘ごとに**解消したか**を判定する | 編集案で本当に改善されたかを、項目の中身の単位で確かめる |

変えないもの：必須条件（5つ）、合格ラインの95点とその意味、○・△・× の点数の付け方（△は50%）、「人」が判定する項目（AI は「要人間確認」）、対象外は記事種類単位で決めること。

## 2. 評価の4層

| 層 | 内容 | 使い方 |
| --- | --- | --- |
| ① 公開の条件 | 必須条件5つ ＋ **記事の型の★の項目が × でないこと**（新） | 1つでも満たさなければ、点数に関係なく公開不可 |
| ② 総合品質 | 100点満点（3章の項目の合計）。95点以上が合格 | 公開してよい完成度か |
| ③ 観点ごとの適合度 | ②と同じ判定を、観点ごとに集計した割合（%）（4章） | どこを直せば伸びるか。**合否には使わない** |
| ④ 実績 | Search Console・GA4 の数字（表示回数・クリック率・掲載順位・アクセス） | 点数にしない。③と比べて、次にやることを決める（S4 の画面） |

## 3. 採点項目（共通基準 2.0.0。合計100点）

* 判定は ○（満たしている）・△（一部不足）・×（満たしていない）。△ は配点の50%。
* 「判定の基準」は ○ と △ の条件。どちらにも当てはまらなければ ×。
* 「観点」は、その項目の判定を集計する観点（4章）。
* 判定者が「人」の項目は、AI は「要人間確認」とし、AI の点数に含めない（今と同じ）。

## 4. 観点ごとの適合度

### 4-1. 観点

| キー | 観点 | 何を見るか |

| `people` | People-first | 役に立つか・独自性・経験・正確さ・信頼性（Google の考え方への適合。**Google の評価そのものではない**） |
| `seo` | SEO | 検索エンジンが内容を理解しやすいか（見出し・キーワード・内部リンク） |

| `nav` | 回遊 | ロードマップ・関連記事・次に読む記事への導線 |
| `mon` | 収益化 | 合う教材を、邪魔にならない位置で、理由つきで紹介しているか |

### 4-2. 計算

* 観点の適合度（%）＝ その観点に関係する項目の得点の合計 ÷ 配点の合計 × 100。
* 1つの項目は、関係するすべての観点に、同じ得点で数える（判定は1回だけ）。
* 対象外の項目と、AI の評価での「要人間確認」の項目は、その観点の計算から除く。
* 観点の適合度は、合否に使わない。弱い観点と、その観点を下げている指摘を示すために使う。

## 6. 指摘・対応・確認（S2・S3 で作る仕組み）

### 6-1. 品質診断の指摘

○ でない項目ごとに、AI は次を出す。

| 欄 | 内容 | 例 |
| --- | --- | --- |
| 番号 | 指摘の番号 | 3 |
| 項目 | 採点項目のキー | `type.do_result` |
| どこが | 見出しの名前か、該当する文の引用 | 見出し「onsubmit の書き方」のコードの後 |
| 何が足りないか | 判定の基準に照らした問題 | コードの実行結果（送信が止まる様子）がない |
| どう直すか | 満たすべき状態 | コードの直後に、空欄で送信したときの表示を「実行結果」として示す |

### 6-2. 記事改修の対応表

記事改修は、指摘の一覧を「直すべきこと」として受け取り、指摘ごとに次を出す。

| 欄 | 内容 |
| --- | --- |
| 番号 | 指摘の番号 |
| 対応 | 直した（どこをどう直したか）／直さなかった（理由。例：人の実体験が必要） |

### 6-3. 改修後の確認

編集案の品質診断では、通常の採点に加え、元の指摘ごとに「解消・一部解消・未解消」を判定する。編集案の画面に、指摘 → 対応 → 改修後の判定と、観点ごとの変化を並べる。未解消の指摘は、次の改修に引き継ぐ。
