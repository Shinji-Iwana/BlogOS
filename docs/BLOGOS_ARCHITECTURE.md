本書は、BlogOSを実現するためのシステム全体の構造、各機能の責務、データの流れ、および各コンポーネント間の関係を定義する。

本書では、BlogOSの理想的なアーキテクチャを定義する。現在のBlogOSに存在するファイル、クラス、ディレクトリ構成、実装方法などによって、本書の設計を制限してはならない。

現在の実装と本書の設計に差異がある場合の扱いは `CLAUDE.md` に従う。

本書は、以下の規則を定義する唯一の場所とする（D-12-03）。他の文書はこれらを本書の節番号で参照する。

* 参照元と正本の区分（3章）
* WordPress APIを直接呼んでよい場面（3-4）
* AI機能の段階の区分（18-2）
* 用語集（29章）

本文中の `（D-xx-xx）` は、根拠となる決定事項（`BLOGOS_DECISIONS.md`）を示す。

# 2. システム全体像

## 2-1. BlogOSの位置付け

BlogOSは、複数のWordPressブログと各種外部サービスを接続し、それらの情報をBlogOS側で集約・管理・分析するシステムである。

基本的な構造は以下とする。

                    ┌─────────────────────┐
                    │  利用者（ログイン） │
                    │  PC / スマートフォン│
                    └──────────┬──────────┘
                               │ HTTPS
                               ▼
                    ┌─────────────────────┐
                    │  BlogOS（XServer）  │
                    │                     │
                    │  UI / Application   │
                    │  Logic / Database   │
                    │  cron / Queue       │
                    └──────┬───────┬──────┘
                           │       │
              ┌────────────┘       └──────────────┐
              ▼                                   ▼
    ┌──────────────────┐                ┌──────────────────┐
    │    WordPress     │                │  External APIs   │
    │                  │                │                  │
    │ WordPress REST   │                │ GA4              │
    │ API              │                │ Search Console   │
    │ + BlogOS連携用の │                │ AdSense          │
    │   拡張（テーマ） │                │ AI（OpenAI）     │
    └──────────────────┘                └──────────────────┘

BlogOSは、外部サービスそのものを置き換えるのではなく、複数サービスから取得した情報を一元的に扱う管理基盤として機能する。

# 3. BlogOSとWordPressの関係

## 3-1. 基本的な役割分担

### WordPress

WordPressは、ブログを実際に公開・運営するCMSとして利用する。

主な役割：

* ブログサイトの公開
* 投稿・固定ページの公開
* カテゴリ・タグ・ユーザー・メディアの管理
* WordPress内部の各種管理

### BlogOS

BlogOSは、ブログ運営全体を管理・分析・改善するための管理システムとして利用する。

主な役割：

* 複数ブログ管理
* WordPress情報の集約とDB保存
* 差分管理・履歴管理
* 記事管理（編集案、管理情報）
* 記事評価
* Google関連情報の集約
* AIによる記事支援
* ブログ全体の分析・管理

---

## 3-2. 参照元と正本

「情報源」という語は使わず、次の2つを区別する（D-01-01）。

| 用語 | 意味 |
| --- | --- |
| **参照元** | 画面表示・検索・分析・AIへの入力が読むデータの場所 |
| **正本** | データが食い違ったときに正とする側 |

**参照元は常にBlogOS DBとする。**

**正本はデータの種類ごとに定める**（D-01-02）。

| データ | 正本 | BlogOS DBの位置付け |
| --- | --- | --- |
| WordPress由来（投稿・固定ページ・カテゴリ・タグ・ユーザー・メディア・サイト設定・ステータス等の定義・カスタム投稿タイプ等） | WordPress | 最後に同期・反映した時点の写し |
| 反映前の編集案・新規記事 | BlogOS | 正本。WordPressへの反映成功後、その内容の正本はWordPressへ移る |
| BlogOS独自データ（評価・AI出力・記事の管理情報・履歴・同期記録・反映記録） | BlogOS | 正本 |
| Google由来の指標 | Google | 取得時点の写し（取得期間を記録する） |

この区分により、次のように振る舞う。

* WordPress側の変更を同期で検出した場合、正本であるWordPressの値をDBへ取り込む（3-3）。
* BlogOSからWordPressへ反映した場合、送信した内容ではなくWordPressの返却値でDBを更新する（13-5）。
* 同期処理は、BlogOS独自データを変更しない。

---

## 3-3. WordPressとBlogOSのデータの関係

同期では、WordPressの現在の状態とBlogOS DBを比較する（D-01-04）。

WordPressの現在情報
        │
        ▼
   APIから取得
        │
        ▼
BlogOS DBの保存情報と比較
        │
   ┌────┴──────────────┐
   │                   │
一致               差分あり
   │                   │
   ▼          ┌────────┴────────┐
何もしない     │                 │
          作業中の編集案       作業中の編集案
            なし                あり
               │                 │
               ▼                 ▼
         DBを更新・履歴記録   「競合」として記録
         ・通知              人間が判断
                            （DBは自動更新しない）

競合を解消する方法（WordPressの変更を編集案に取り込む／編集案を破棄する／編集案で上書きする）は `BLOGOS_WORDPRESS_API.md` 21-2 で定義する（D-15-03）。

---

## 3-4. WordPress APIを直接呼んでよい場面

通常の画面表示や検索のたびにWordPress APIを呼び出さない。WordPress APIを直接呼び出してよいのは、次の場面に限る（D-01-10）。

1. API確認画面
2. ブログ登録・接続確認
3. 同期（毎日の自動同期、手動同期、初回取得、回復処理）
4. WordPressへの反映と、反映直前の競合確認
5. 反映結果の取得

ログイン時やダッシュボードの通知は、DBに記録した同期結果を表示するだけで、WordPress APIは呼ばない（D-01-05）。

# 4. BlogOSの基本設計思想

## 4-1. DBを参照元とした情報管理

BlogOSでは、取得済みの情報についてBlogOS DBを参照元とする。

これは、以下を実現するためである。

* APIアクセス削減
* 高速な画面表示
* 検索性向上
* 履歴管理
* データ分析
* 複数サービスの情報統合
* BlogOS独自情報の付加
* 外部サービスが停止しても保存済みの情報を確認できること

---

## 4-2. 外部サービスとの境界を明確にする

WordPress、Google API、AIサービスなどの外部サービスとBlogOS内部の処理を明確に分離する。

外部サービス
    ↓
External API Client
    ↓
DTO
    ↓
Service
    ↓
Repository
    ↓
Model / Database

外部APIとの通信処理を、ControllerやBladeなどに直接記述しない。

---

## 4-3. UIとデータ処理を分離する

画面表示を担当する処理と、データ取得・保存・分析などを担当する処理を分離する。

Browser
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database

Controllerに業務処理を集中させない。

---

## 4-4. 一つの責務を一つの層に集約する

* Controller：HTTPリクエストと画面・レスポンスの制御
* Service：業務処理
* Repository：DBアクセス
* Model：DBデータ構造
* DTO：外部データの保持
* API Client：外部API通信
* Job：時間のかかる処理の非同期実行

---

               │

# 6. Presentation Layer

## 6-1. 役割

Presentation Layerは、利用者へ情報を表示し、利用者からの操作を受け付ける。

主な構成要素：

* Blade
* HTML
* CSS
* JavaScript

画面は、PCとスマートフォンの両方で利用できるよう、画面サイズに応じて表示を調整する（D-03-06）。

### テーマ

画面の見た目は、テーマとして切り替えられるようにする（D-16-01）。

* 使用するテーマは `config/blogos.php` の `theme` で指定する（現在は `blank`＝装飾なし、今後 `ironman` 等を追加）。
* テーマのViewは `resources/views/themes/{テーマ名}/` に置く。
* テーマは見た目だけを担当し、表示するデータ・業務処理・ルートはテーマによって変えない。どのテーマでも同じControllerが同じデータを渡す。
* 当面は `blank` で機能を作り、システムの構築後に見た目を整える。

---

## 6-2. Presentation Layerの責務

* データ表示
* 入力フォーム表示
* ユーザー操作の受付
* 表示上の条件分岐
* UI上の状態表示

業務ロジックやDBアクセスを直接担当しない。Bladeの中で関連データを参照してクエリを発生させること（遅延読み込み）を禁止する（D-11-01）。

---

## 6-3. 画面の種類

BlogOSの画面は、次の種類に分ける（D-11-05）。用語の定義は29章を参照する。

| 画面の種類 | 目的 | データの取得元 |
| --- | --- | --- |
| API確認画面 | WordPress APIが実際に返す内容を確認する | その場でWordPress APIを呼び出す（DBに保存しない） |
| DB確認画面 | BlogOS DBの保存内容・履歴・テーブルの状態を確認する | BlogOS DB |
| 業務画面 | 記事管理・編集案・同期・評価・AIなど | BlogOS DB |

API確認画面とDB確認画面は目的が異なるため、同一の画面・同一の処理として混在させない。

---

# 7. Controller Layer

## 7-1. 役割

Controllerは、HTTPリクエストを受け取り、適切なServiceを呼び出し、結果を画面またはレスポンスへ渡す。

---

## 7-2. Controllerの責務

* Requestの受け取り
* 入力値の取得
* Validationの呼び出し
* Serviceの呼び出し
* Responseの生成
* Viewへのデータ受け渡し
* Redirect

---

## 7-3. Controllerの分類

Controllerは次の名前空間に分ける（D-11-02）。

| 名前空間 | 用途 |
| --- | --- |
| `App\Http\Controllers\WordPressApi` | API確認画面 |
| `App\Http\Controllers\Database` | DB確認画面 |
| `App\Http\Controllers\Api` | BlogOS自身がJSONを返すエンドポイント（同期状態の取得など） |
| 機能ごとの名前空間 | 業務画面 |

Controllerは画面ごとではなくリソースごとに作り、`index` / `show` 等のメソッドで操作を分ける（D-11-04）。ルート名の規則は `BLOGOS_DEVELOPMENT_RULES.md` で定義する。

---

## 7-4. Controllerに業務ロジックを集中させない

以下はServiceなどの適切な層で処理する。

* WordPress API取得
* 差分比較
* DB保存
* 履歴作成
* AI処理
* Google API処理

時間のかかる処理（同期、AIの実行）は、ControllerからJobとして登録するだけにし、Webリクエストの中で実行しない（D-04-07）。

---

# 8. Service Layer

## 8-1. 役割

Serviceは、BlogOSの業務処理を担当する。BlogOSにおける主要な処理はServiceを中心として構成する。

---

## 8-2. Serviceの責務

* API取得処理の制御
* データ変換・処理
* DB保存処理の制御
* 差分検出
* 履歴作成
* 複数データの組み合わせ
* 外部サービス連携処理
* 記事評価
* AI処理の制御

---

## 8-3. Serviceの粒度

Serviceは、責務が明確になる単位で分割する。一つのServiceに無関係な機能を大量に集約しない。

---

# 9. Repository Layer

## 9-1. 役割

Repositoryは、BlogOS DBへのアクセスを担当する。

---

## 9-2. Repositoryの責務

* 一覧取得
* ID指定取得
* 条件検索
* 保存
* 更新
* 削除
* 関連データ取得

---

## 9-3. ServiceとRepositoryの関係

Controller
    ↓
Service
    ↓
Repository
    ↓
Model / DB

**DBへのアクセスは、すべてRepositoryを経由する。例外は設けない**（D-11-01）。単純な取得であっても、Repositoryのメソッドを用意する（中身の薄いメソッドでよい）。

ControllerやBladeからModelを直接使ってDBへアクセスしない。

---

# 10. Model Layer

## 10-1. 役割

Modelは、BlogOS DBのテーブル・データ構造を表現する。

---

## 10-2. Modelの責務

* テーブルとの対応
* Primary Key
* Fillable
* Cast（認証情報の暗号化キャストを含む）
* Relationship
* Modelレベルのデータ定義

---

## 10-3. Modelに業務処理を集中させない

複雑な業務処理をModelに集中させず、Serviceへ分離する。

---

# 11. DTO Layer

## 11-1. 役割

DTOは、外部APIなどから取得したデータをBlogOS内部で扱うためのデータ構造として利用する。

---

## 11-2. WordPress API DTO

WordPress APIから取得したレスポンスは、APIで取得できた情報をそのまま保持する。フィールド名や値の意味を変えない。

これにより、

* API取得結果確認
* 差分確認
* DB保存
* API仕様変更への対応

を行いやすくする。

APIレスポンスはDTOがメモリ上で保持し、原文をDBへ保存しない。ただし、エラー時の応答本文は全文を保存する（D-10-03、24-2）。

---

## 11-3. DTOとDBの関係

DTOとDB Modelは同一のものとして扱わない。

WordPress API Response
        ↓
      DTO
        ↓
Service（変換・差分確認）
        ↓
      Model
        ↓
      Database

DBへ保存する項目は `BLOGOS_DATABASE.md` に基づいて決定する。

---

# 12. External API Client Layer

## 12-1. 役割

External API Clientは、BlogOSと外部サービスとの通信を担当する。

対象：

* WordPress REST API
* Google Analytics API
* Google Search Console API
* Google AdSense API
* AI API（OpenAI）

Clientは `app/Clients/` に置く（D-11-03、22章）。

---

## 12-2. API Clientの責務

* URL生成
* HTTP通信
* 認証
* Request送信
* Response受信
* timeout
* 通信エラー処理
* API固有の通信処理

認証情報は、呼び出し元から対象ブログを受け取り、DBに暗号化して保存された認証情報を使う（25章）。

---

## 12-3. 業務ロジックとの分離

API Clientは通信だけを担当する。DB保存、差分判定、記事評価などBlogOS独自の業務ロジックをAPI Clientへ持ち込まない。

---

# 13. WordPress API連携アーキテクチャ

## 13-1. 基本構造

取得の流れ：

WordPress REST API
    ↓
WordPress API Client
    ↓
DTO
    ↓
Service
    ↓
Repository
    ↓
DB

取得条件・差分の検出方式・取得順序の詳細は `BLOGOS_WORDPRESS_API.md` で定義する。

---

## 13-2. WordPress APIの種類ごとの分離

WordPress APIの種類ごとに、ServiceやDTOを分離する。

* Site / Settings
* Post
* Page
* Category
* Tag
* Author（Users API）
* Media
* Status
* Type
* Taxonomy
* カスタム投稿タイプ・カスタムタクソノミー

---

## 13-3. API取得とDB保存の分離

API取得とDB保存を同一処理に固定しない。

API取得とDBへの保存を別々に実行できる構造とし、APIレスポンスの確認、差分確認、再保存などを柔軟に行えるようにする。

---

## 13-4. 同期処理

同期は次の流れで行う（D-01-03、D-04-01、D-04-05）。

同期の開始（毎日のcron / 「今すぐ同期」/ ブログ登録時）
    ↓
ブログ単位のロックを取得
    ↓
同期の実行記録を作成（sync_runs）
    ↓
回復処理（止まっている反映記録の処理。13-6）
    ↓
リソースごとに：
    IDと更新日時の一覧を取得
        ↓
    DBと比較して新規・変更・削除を判定
        ↓
    新規・変更分だけ詳細を取得
        ↓
    3-3 の規則でDB更新・履歴記録・競合の記録
        ↓
    リソースごとの件数を記録（sync_run_resources）
    ↓
対応が必要な問題を記録（sync_issues）
    ↓
実行記録を完了
    ↓
ロックを解放

* トランザクションは1レコード単位（本体・関連・履歴）とし、同期全体を1つのトランザクションにしない。
* WordPressとのHTTP通信を、DBトランザクションの中で行わない。
* 同期の途中で一部のリソースが失敗しても、他のリソースの結果は残し、実行記録を `partial` とする。

---

## 13-5. WordPressへの反映

記事の反映は、編集案を通して行う（D-01-06〜D-01-09）。

人間が反映を承認
    ↓
反映記録を作成（状態：pending）
    ↓
反映直前の競合確認
（WordPressの最新 modified_gmt と、編集案の基準バージョンを比較）
    ├─ 異なる → 反映を中止し、差分を人に示す
    ↓ 同じ
状態を sent に更新
    ↓
WordPress API Clientで送信
    ↓
応答を受信 → 直ちに応答（wordpress_id、modified_gmt）を保存（wp_succeeded）
    ↓
DBトランザクション：
    posts / pages 等をWordPressの返却値で更新
    履歴を記録（変更元：blogos_push）
    編集案を「反映済み」に更新
    ↓
状態を completed に更新

* 反映に成功したら、必ずWordPressの返却値でDBを更新する。送信した内容をそのまま保存しない。
* `sent` / `unknown` / `wp_succeeded` の反映記録がある編集案は、再反映できないようにロックする。
* 反映は人間の承認を必須とする。公開・削除・設定変更は、さらに確認画面を挟む（18-2 の段階2・3）。
* カテゴリ・タグ・メディアは編集案を持たない。承認時の入力内容と、画面を開いた時点の値を反映記録に保存し、反映直前に最新の値と比べて競合を確認する（D-15-05、WORDPRESS_API 21-3）。

---

## 13-6. 反映の失敗と回復

| 失敗した位置 | WordPress | DB | 扱い |
| --- | --- | --- | --- |
| 送信前 | 変化なし | 変化なし | `failed`。やり直せる |
| 送信中（タイムアウト等） | 不明 | 変化なし | `unknown`。人が確認する |
| 受信後のDB更新 | 反映済み | 古いまま | `wp_succeeded` のまま残る。回復処理で再取得してDBを更新する |

* 回復処理は、毎日の同期の最初に実行する（変更元：`blogos_recovery`）。
* 新規作成が `unknown` になった場合、BlogOSは、反映直前の時刻以降に作成された下書きを表示し、人が照合する。WordPress側の拡張（13-7）が有効なブログでは、投稿メタの編集案IDで照合できる。

---

## 13-7. WordPress側の拡張（BlogOS連携用）

BlogOSは、WordPress側に次の拡張を置く（D-01-12）。

| 項目 | 内容 |
| --- | --- |
| 目的 | 新規作成がタイムアウトしたときに、作成された投稿を確実に照合する |
| 内容 | 投稿メタ `_blogos_draft_id` を `register_post_meta` で登録し、REST APIで読み書きできるようにする（編集権限のあるユーザーに限定） |
| 置き場所 | テーマの基盤 `Theme-SI-Original` の `functions.php` から読み込む別ファイル（例：`inc/blogos-connector.php`） |
| コードの管理 | テーマのリポジトリ（`Develop/Theme`）で管理する |
| 判定 | BlogOSは、ブログの接続確認時にこの拡張が有効かどうかを判定し、無効なブログでは人による照合で運用する |

注意：

* STINGER8で運用している間は、拡張は無効である。
* 基盤テーマを修正しても、既にコピーして作成した派生テーマには自動では反映されない。別ファイルにしておくことで、派生テーマへの差し替えを容易にする。

# 14. DBアーキテクチャ

## 14-1. DBの役割

BlogOS DBは、BlogOSが扱う情報の参照元である。

DBには、

* WordPressから取得した情報（写し）
* BlogOS独自の管理情報
* 編集案
* 履歴情報
* 同期記録・反映記録
* 評価情報・AI実行記録
* Google関連の情報

を保存する。

---

## 14-2. WordPress由来のテーブルとBlogOS独自のテーブルを分ける

WordPress APIの取得結果を保持するテーブルには、WordPress由来の列だけを持たせる。BlogOS独自の情報（記事の管理情報、編集案など）は別のテーブルで管理する（D-01-11）。

同期処理は、WordPress由来のテーブルだけを更新する。

---

## 14-3. DBとWordPressの関係

DBはWordPressの完全なコピーではない。

WordPress API
        ↓
取得可能な情報
        ↓
BlogOSとして保存すべき情報
        ↓
BlogOS DB

具体的な保存項目・ID命名・履歴・削除・保存期間は `BLOGOS_DATABASE.md` で定義する。

# 15. 履歴管理アーキテクチャ

## 15-1. 履歴管理の目的

履歴管理によって、

* 何が変更されたか
* いつ変更されたか
* 変更前は何だったか
* 変更後は何になったか
* 何が変更を引き起こしたか（変更元）
* どの処理（同期・反映）による変更か

を確認できるようにする。

---

## 15-2. 履歴が発生するタイミング

* WordPress同期による変更（初回取得を含む）
* BlogOSからWordPressへの反映
* 反映の回復処理
* BlogOS上での手動編集（BlogOS独自データ）
* AIによる生成（BlogOS独自データ）

AIは、WordPress由来のテーブルを直接変更しない（18-2）。

---

## 15-3. 履歴と現在値を分離する

現在のデータ
    ↓
通常テーブル

過去の変更
    ↓
Historyテーブル

履歴は、変更した項目ごとに1行で記録し、同時に起きた変更をひとまとまりとして扱う（D-05-09）。具体的な構造と変更元の列挙値は `BLOGOS_DATABASE.md` で定義する。

# 16. ブログ切替・複数ブログ管理

## 16-1. 複数ブログを管理する

BlogOSでは複数のWordPressブログを登録できる。各データは、どのブログに属するかを識別できるようにする。

---

## 16-2. 現在選択中のブログ

選択中のブログは `blogs.is_selected` で管理し、URLには含めない（D-02-05）。

* 切り替えは1つのトランザクションで行う（全ブログの選択を解除 → 対象ブログを選択）。
* 更新系の画面では、表示時の `blog_id` をフォームに含め、送信時に現在の選択中ブログと照合する。一致しない場合は処理を止めて警告する（別タブで切り替えた場合の誤操作を防ぐ）。
* 同期・Job・Commandなどの自動処理は `is_selected` を使わず、対象ブログを明示的に受け取る。
* 将来、複数ユーザーに対応する際は、ユーザー単位の選択に移行する。

---

## 16-3. ブログIDによるデータ識別

Blog
 ├─ Settings
 ├─ Credentials
 ├─ Posts / Pages
 ├─ Categories / Tags
 ├─ Authors
 ├─ Media
 ├─ Statuses / Types / Taxonomies
 ├─ Custom Contents / Custom Terms
 ├─ Drafts / Article Managements
 ├─ Sync Runs / Push Operations
 └─ Histories

---

## 16-4. アーカイブ

アーカイブしたブログ（`archived_at` あり）は、同期・反映・AIの対象から外す。データは残し、元に戻せる。ブログの完全削除は別の操作とし、WordPress側には何もしない（D-09-06）。

---

# 17. 記事管理アーキテクチャ

## 17-1. 記事の定義

BlogOSで「記事」とは、**投稿（posts）と固定ページ（pages）**を指す（D-08-01）。

記事単位で扱うテーブル（編集案、記事の管理情報、評価、AI実行記録、反映記録、記事内メディア等）は、`post_id` と `page_id` のどちらか一方だけを持つ形で記事を参照する。

カスタム投稿タイプは記事に含めない。同期と閲覧だけの対象とする（D-10-04）。

---

## 17-2. 記事の基本データフロー

WordPress
    ↓
Posts / Pages API
    ↓
DTO
    ↓
Service
    ↓
Repository
    ↓
posts / pages（WordPressの写し）

同期時に、本文から次の情報を抽出して保存する（D-08-04、D-10-02）。

* 同じブログ内へのリンク（内部リンク）
* 本文中で使われているメディア

---

## 17-3. 記事の管理情報

記事ごとに、BlogOS独自の管理情報（記事種類、検索意図、キーワード、作業状態、記事同士の関係）を持つ（D-08-02〜D-08-04）。

記事種類などの選択肢は、そのブログに適用する品質基準のブログ別の定義に従う。

設計上の関係（人が登録）と実際の内部リンク（自動抽出）を比べることで、リンク漏れや孤立記事を検出する。

---

## 17-4. 記事評価

記事評価は、WordPressの投稿データとは別のBlogOS機能として扱う。

記事（DB）
    ↓
品質基準（共通基準＋ブログ別の定義）
    ↓
評価（AI または 人間）
    ↓
評価結果（基準のバージョン、評価した主体、項目ごとの判定、点数）

合格は、人間が「必須条件をすべて満たし、95点以上」と確定した場合とする（D-06-02、D-07-03）。

---

## 17-5. 記事の作成・改修の流れ

記事（または新規）
 ↓
編集案を作成（人 または AI。基準バージョンを記録）
 ↓
人間による確認・修正
 ↓
評価（必要に応じて）
 ↓
人間が反映を承認
 ↓
WordPressへ反映（13-5）
 ↓
posts / pages を返却値で更新

* 新規記事は、反映に成功するまで編集案としてだけ存在する。
* AIの出力をそのまま公開することはしない。

---

# 18. AI機能アーキテクチャ

## 18-1. AIの位置付け

AIは、BlogOSの業務を支援する機能として扱う。AIサービスそのものをBlogOSの中心ロジックにしない。

本書でいう「AI」は**BlogOSのAI機能**を指し、開発に使う**開発支援AI**（Claude Code等）とは区別する（D-07-09）。

---

## 18-2. AIの段階の区分

AIに許可する操作を次の段階に分ける（D-07-01、D-07-02）。

| 段階 | 内容 | 例 | AIによる実行 |
| --- | --- | --- | --- |
| 0：分析・提案 | BlogOSのデータを変更しない | 品質診断、SEO分析、構成案、改善案 | 可（人の操作をきっかけに） |
| 1：編集案の作成 | 編集案テーブルにだけ書き込む | 新規記事の案、改修案 | 可（人の操作をきっかけに） |
| 2：WordPressへの反映 | 編集案をWordPressへ送る | 下書きとして更新 | 不可。必ず人が承認する |
| 3：重大な操作 | 公開・削除・WordPressの設定変更 | 記事の公開 | 不可。人が承認し、さらに確認画面を挟む |

* AIは、人が画面で実行したときだけ動く。定期実行はしない。
* AIが作成した記事の自動公開はしない。
* AIはWordPressへ直接アクセスしない。

---

## 18-3. AI処理の基本構造

BlogOS DB
    ↓
AI Service（AI実行テンプレートと品質基準から指示文を作成）
    ↓
AI Executor（実行方式の切り替え）
    ├─ 手動実行：指示文を画面に表示 → 利用者がChatGPT等で実行 → 回答を画面から取り込む
    └─ API実行：AI Client → AI API
    ↓
AI Service（出力を検証し、編集案・評価結果として保存）
    ↓
利用者による確認

### AI Client

AIサービスとの通信だけを担当する。

### AI Executor

実行方式（手動／API）の違いを吸収する共通のインターフェースと、その2つの実装。実行方式は、実行モード（品質診断、記事作成など）ごとに設定で切り替える（D-07-06）。当面は手動実行を標準とする。

### AI Service

* 何をAIへ渡すか（記事、品質基準の必要な部分だけ）
* どのテンプレート・モデルを使うか
* AIの結果をどう扱うか

を制御する。

---

## 18-4. AI実行テンプレートと品質基準の置き場所

BlogOSが実行時に読み込むファイルは、リポジトリ内に置き、Gitで管理する（D-07-05）。

| 種類 | 置き場所（例） |
| --- | --- |
| AI実行テンプレート | `resources/ai/templates/` |
| 品質基準（共通基準） | `resources/quality/common/` |
| 品質基準（ブログ別の定義） | `resources/quality/blogs/{ブログ}/` |

* 費用を抑えるため、AIには品質基準の全文ではなく、記事種類に対応するテンプレートと採点表など必要な部分だけを渡す。
* テンプレートと品質基準にはバージョンを付け、AI実行記録に記録する。

---

## 18-5. AIの実行回数と受け入れ

* 1回の指示につき1回だけ実行する（実行回数は設定値。初期値1）（D-07-03）。
* AIの出力を受け入れるかどうかは人が判断する（受け入れの目安の点数は設定値。初期値90点）。
* AIでは判定できない評価項目は「要人間確認」とし、AIの採点から外す。

---

## 18-6. AI出力と生成方法の記録

AIの実行ごとに、次を記録する（D-07-04、D-07-07）。

* 実行方式（手動／API）、提供元、モデル（API実行では応答に含まれる正確なモデル名、手動実行では利用プランと画面に表示されたモデル名）、推論の深さ
* AI実行テンプレートと品質基準のバージョン
* 入力と出力の全文、トークン数・費用の目安、状態、エラー
* 関連する編集案・評価結果

記事からは「記事 → 反映記録 → 編集案 → AI実行記録」の順にたどり、どの版をどの方法で作ったかを確認できるようにする。これにより、モデルや実行方式ごとの評価を比較できる。

---

## 18-7. 費用と実行の制限

* 月の費用上限と、1回あたりのトークン上限を設定値として持つ（D-07-08）。上限に達したらAPI実行をできないようにする。
* API実行はJobとして実行し、画面は状態を読んで表示する。
* 使用するモデルはコードに直接書かず、設定またはテンプレートで指定する。

---

# 23. 外部APIと内部データの境界

## 23-1. 外部APIのデータ形式をそのまま内部全体へ持ち込まない

外部APIのレスポンス形式は、外部サービス側の仕様である。BlogOS内部の設計を外部APIのレスポンス形式に完全依存させない。

## 23-2. DTOによる境界

外部APIから取得したデータは、DTOを介してBlogOS内部へ渡す。これにより、外部API仕様の変更がBlogOS全体へ直接波及することを防ぐ。

* APIレスポンスエラー

* AIエラー
* システムエラー

## 24-2. 外部APIエラー

外部APIとの通信で発生したエラーについては、

内部的なエラー情報をそのまま利用者へ表示せず、必要な情報を整理して表示する。開発・調査に必要な情報はログや記録に残す。

# 25. セキュリティ

BlogOSでは、次を基本方針とする（D-03-01〜D-03-06）。

* BlogOSへのアクセスはログインを必須とし、通信はHTTPSとする。
* 外部サービスの認証情報は、BlogOSの中で安全に保管し（ブログごとの認証情報はDBに暗号化して保存する）、画面・ログに出さない。
* API Clientは、対象ブログの認証情報を受け取って通信する（12-2）。

具体的なルール（保存方法、暗号化の鍵の管理、画面での扱い、WordPress側で発行するApplication Password）は `BLOGOS_DEVELOPMENT_RULES.md` 13章で定義する（D-15-06）。

# 27. アーキテクチャ上の原則

## 原則1：責務を分離する

一つのクラス・層に複数の異なる責務を集中させない。

## 原則2：外部APIと内部処理を分離する

外部API通信処理とBlogOS独自の業務ロジックを分離する。

## 原則3：DBを参照元とする

取得済みの情報については、BlogOS DBを参照元とする。

## 原則4：複数ブログを前提とする

一つのブログだけを前提とした設計を行わない。

## 原則5：APIレスポンスとDB構造を分離する

WordPress APIのレスポンス構造とBlogOS DBの構造を完全に同一視しない。

## 原則6：現在の実装に設計を合わせない

既存コードの都合だけを理由として理想設計を変更しない。

将来の拡張性は確保するが、現時点で必要のない抽象化やクラスを過剰に作成しない。

# 28. 実行基盤

## 28-1. 前提

BlogOSはXServer（共用サーバー）で動作させる。常駐プロセスを動かせないため、定期実行と時間のかかる処理は、cronとQueueで実行する（D-04-07）。

---

## 28-2. 実行方式

| 要素 | 方式 |
| --- | --- |
| 定期実行 | XServerのcronから `php artisan schedule:run` を実行する。毎日の同期、保存期間を過ぎた記録の削除などをSchedulerに登録する |
| Queue | databaseドライバーを使う。cronから `php artisan queue:work --stop-when-empty --max-time=<秒数>` を定期的に起動し、たまった処理を片付けたら終了させる |
| 手動同期・AI実行 | Webリクエストの中では実行せず、Jobとして登録する。画面は状態を定期的に読んで進み具合を表示する（`Controllers\Api` のエンドポイントを使う） |
| 二重実行の防止 | ブログ単位でロックする（キャッシュロックと、`running` 状態の同期の実行記録の確認を併用）。異常終了でロックが残った場合に備え、一定時間で解除する |
| トランザクション | 1レコード単位（本体・関連・履歴）。外部APIとの通信をトランザクションの中で行わない |

確認事項：XServerのcronの最短間隔と、PHPの実行時間の上限（CLI・Web）。確認後、`--max-time` などの値を決める。

# 29. 用語集

| 用語 | 定義 |
| --- | --- |
| 参照元 | 画面表示・検索・分析・AIへの入力が読むデータの場所。常にBlogOS DB（3-2） |
| 正本 | データが食い違ったときに正とする側。データの種類ごとに定める（3-2） |
| ホームURL | WordPressの「サイトアドレス」（`home`）。WordPress APIの接続先の基準であり、ブログの識別に使う（`blogs.home`）。「WordPressアドレス」（`url`）とは別物 |
| 記事 | 投稿（posts）と固定ページ（pages）。カスタム投稿タイプは含まない（17-1） |
| 編集案 | BlogOS上で作成・編集中の、WordPressへ未反映の記事内容 |
| 同期 | WordPress APIから取得した情報とBlogOS DBを比較し、DBを更新する処理 |
| 反映 | BlogOSからWordPressへ変更を送る処理 |
| 競合 | 編集案の作業中に、WordPress側で同じ記事が変更された状態 |
| 反映記録 | 反映操作ごとの状態を記録したもの（13-5） |
| 回復処理 | 途中で止まった反映を完了させる処理（13-6） |
| API確認画面 | WordPress APIをその場で呼び出して結果を表示する画面。一覧と詳細がある |
| エンドポイント一覧 | BlogOSが対象とするWordPress APIの一覧 |
| DB確認画面 | BlogOS DBの保存内容・履歴・テーブルの状態を表示する画面 |
| 業務画面 | 記事管理・編集案・同期・評価・AIなどの画面 |
| BlogOSのAI機能 | BlogOSに組み込む、記事の評価・作成・改修などのAI機能 |
| 開発支援AI | 開発に使うAIツール（Claude Code等） |
| 手動実行 | BlogOSが作成した指示文を利用者がChatGPT等に貼り付け、回答をBlogOSに取り込むAIの実行方式 |
| API実行 | BlogOSがAIのAPIを直接呼び出すAIの実行方式 |
| 必須条件 | 1つでも満たさなければ、点数に関係なく公開できない品質の条件（品質基準 `common/scoring.md`） |
| 改修範囲 | 既存記事を改修する際に、実行のたびに指定する範囲（軽微な改善／構成の見直し／全面改修）（品質基準 `common/ai-and-operation.md`） |
| 品質基準のバージョン | 共通基準・ブログ別の定義それぞれのバージョン。評価結果とAI実行記録に記録する |
| 共通基準 | 全ブログに共通する記事の品質基準 |
| ブログ別の定義 | ブログごとの想定読者・記事種類・CTA・HTMLルールなどの品質基準 |
