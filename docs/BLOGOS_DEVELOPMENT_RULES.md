# 1. 本書の目的と位置付け

本書は、BlogOSの開発・改修・保守で守る実装ルールを定義する。

* 「何を実現するか」は `BLOGOS_REQUIREMENTS.md`、「どういう構造か」は `BLOGOS_ARCHITECTURE.md`、「何をどう保存するか」は `BLOGOS_DATABASE.md`、「WordPress APIをどう使うか」は `BLOGOS_WORDPRESS_API.md` で定義する。本書はそれらを**コードでどう実装するか**を定義する。
* 他の文書で定義している規則は、本書では繰り返さず、節番号で参照する。
* 文書間の優先順位、現在の実装との差異の扱い、Claude Code固有の作業手順は `CLAUDE.md` で定義する。
* 本書は、以下を定義する唯一の場所とする。
  * 開発時の優先順位（2章）
  * エラー処理・セキュリティ・テスト・Gitのルール（12〜17章）

本文中の `（D-xx-xx）` は、根拠となる決定事項（`BLOGOS_DECISIONS.md`）を示す。

# 2. 開発時の優先順位と設計原則

## 2-1. 優先順位

判断に迷った場合は、次の順で優先する（D-12-02）。

1. 正確な仕様理解
2. データ整合性
3. セキュリティ
4. 設計との一貫性
5. 保守性
6. 可読性
7. テスト容易性
8. 拡張性
9. パフォーマンス
10. UI
11. 実装速度

## 2-2. 設計原則の扱い

* **YAGNI**：「将来使うかもしれない」という理由だけで、現在不要な機能・抽象化を作らない。
* **DRY**：同じ処理を複数箇所にコピーしない。ただし、無理な共通化で責務が不明確になる場合は共通化しない。
* **KISS**：必要以上に複雑な構造を作らない。
* **SOLID等**：参考にするが、原則そのものを目的にしない。
* 継承は、本当に is-a 関係がある場合だけ使う。Interfaceは、複数の実装を切り替える必要がある場合（例：AIの実行方式。10-1）や、明確な契約が必要な場合だけ使う。

# 3. 作業の進め方

## 3-1. 基本手順

要件の確認
    ↓
設計書の確認
    ↓
関連する既存コードの確認（呼び出し元・呼び出し先・Model・Migration・Route・View・Test）
    ↓
影響範囲の確認（ファイル・DB・Route・API・UI・Test）
    ↓
実装方針の決定
    ↓
実装
    ↓
テスト・動作確認
    ↓
差分の確認（`git diff`）
    ↓
完了報告

## 3-2. 仕様が不明な場合

既存の設計書 → 既存コード → 公式仕様、の順に確認し、それでも不明な場合は未決定事項として明示する。「たぶんこう」「一般的にはこう」「今のコードがこうだから」を根拠に重要な仕様を確定しない。

特に、DB構造・API仕様・認証方式・データの削除・AIの自動実行・WordPressへの公開・外部サービスとの連携は、推測で確定しない。

未決定の事項を実装する必要がある場合は、暫定実装であることをTODOと設計資料に明記する。

## 3-3. 変更範囲

* 依頼された範囲を超えて、命名変更・大規模リファクタリング・UI変更・ファイル移動・DB変更を行わない。
* ただし、作業中に見つけた重大なバグやセキュリティ上の問題は、「問題・影響・原因・対応案」を報告する。
* 大規模な変更は、「現状 → 問題 → 理想 → 変更範囲 → 移行手順 → リスク」を整理し、段階（Phase）に分け、Phaseごとに完了条件を決めてから行う。
* DBの変更が必要な場合はMigrationを先に整理し、Backendのデータ構造が確定してからUIを変更する。

## 3-4. 完了条件

作業は「コードを書いた」時点では完了しない。以下を確認する。

* 要件を満たしている
* 設計書と整合している
* 既存機能を壊していない
* テストが通る
* エラー処理がある
* セキュリティ上の問題がない
* DB・APIとの整合性がある
* 不要な変更をしていない
* `git diff` を確認した

## 3-5. 完了報告

■変更内容
■変更ファイル
■テスト（内容と結果）
■未解決事項
■注意点

問題が残っている場合は「完了」とだけ報告せず、問題・原因・現在の状態・影響・次に必要な対応を示す。未実装のものは「未実装」、一部だけ実装したものは「部分実装」と明示する。

# 4. レイヤー別の実装ルール

各層の責務は `BLOGOS_ARCHITECTURE.md` 5〜12章で定義する。本章は実装上の具体的なルールを定める。

## 4-1. Route

* Routeには、URL・HTTPメソッド・Controller・ルート名・Middlewareだけを書く。処理を書かない。
* ログイン画面以外のすべてのルートに、認証のMiddlewareを付ける（D-03-01）。
* ルート名の規則は 5-3 に従う。画面遷移では、URL文字列ではなくルート名を使う。

## 4-2. Controller

* 「受け取る → Serviceを呼ぶ → 返す」の構造を保つ。
* 入れてよい処理：Requestの取得、Validationの呼び出し、Serviceの呼び出し、Viewへのデータ受け渡し、Redirect、Responseの生成。
* 入れない処理：DBアクセス、WordPress API通信、複雑な業務ロジック・差分判定、大量のデータ変換、AI処理、同期処理。
* 時間のかかる処理（同期、AIの実行）は、Jobとして登録するだけにする（ARCHITECTURE 7-4）。

## 4-3. Request・Validation

* ユーザー入力はサーバー側で必ず検証する。JavaScriptやModalでの検証は、サーバー側の検証の代わりにしない。
* 複雑な検証はForm Requestを使う。
* 検証と業務判断を分ける。例：「URLの形式が正しい」ことと、「そのサイトをBlogOSに登録できる」こと（WORDPRESS_API 29章）は別の処理。
* 更新系のフォームには、画面表示時の `blog_id` を hidden 項目として含め、送信時に現在の選択中ブログ（`blogs.is_selected`）と照合する。一致しなければ処理を止めて警告する（D-02-05）。

## 4-4. Service

* 業務フロー、複数Repositoryの組み合わせ、API Clientの利用、DTOからModelへの変換、同期、差分判定、履歴の作成を担当する。
* 機能ごとに分割する（例：`PostService`、`CategoryService`、`AuthorService`、`SyncService`）。`WordPressService` のような巨大なServiceを作らない。

## 4-5. Repository

* **DBへのアクセスは、すべてRepositoryを経由する。例外は設けない**（D-11-01）。単純な取得でも、Repositoryのメソッドを用意する。
* Repositoryは「DBからどう取得・保存するか」だけを担当する。API通信、AI処理、業務判断、画面向けの表示加工を入れない。

## 4-6. Model

* テーブルとの対応、`fillable`、`casts`、リレーション、scope、Model固有の単純な処理を担当する。
* 外部サービスとの通信、複雑な業務フロー、表示処理を入れない。
* `fillable` を適切に設定し、意図しない属性が更新されないようにする（Mass Assignment対策）。
* 認証情報の列は `encrypted` キャストを使い、`$hidden` で配列化・JSON化の対象から外す（D-03-02）。

## 4-7. DTO

* WordPress APIの応答を、フィールド名・値の意味を変えずに保持する（WORDPRESS_API 3-2）。
* DTOをそのままModelとして使わない。
* APIが `null` を返した場合、勝手に空文字や `0` に変換しない。DBの都合で変換する場合は理由をコメントに書く。

## 4-8. API Client

* 外部サービスとのHTTP通信だけを担当する（URL生成、認証、送受信、timeout、HTTPエラー処理）。
* APIのURLは、API Clientだけで組み立てる。各Serviceで組み立てない。
* DB保存、業務判断、差分判定を入れない。
* どのブログに対する通信かを明示して受け取り、そのブログの認証情報を使う。

## 4-9. Job・Command

* Job・Commandは、同期・反映・AI実行などの入口であり、処理そのものはServiceに任せる。
* 対象ブログを明示的に受け取る。`blogs.is_selected` を使わない（D-02-05）。
* 再実行されてもデータが壊れないようにする（6-6）。

## 4-10. Blade・JavaScript・CSS

* Bladeは表示だけを担当する。DB検索、API通信、複雑な業務ロジック・データ加工を書かない。
* Bladeの中で関連データを参照してクエリを発生させない（遅延読み込みの禁止。6-5）。表示に必要なデータはController・Serviceで準備する。
* JavaScriptは画面上の操作だけを担当する。API通信（BlogOS自身の `Controllers\Api` を除く）やDB処理の責務を持たせない。
* 画面はPCとスマートフォンの両方で使えるよう、画面サイズに応じて表示を調整する（D-03-06）。
* CSSの変更でPHPの処理を変えない。PHPの変更のために不要なCSSを変えない。

# 5. ディレクトリ・命名

## 5-1. ディレクトリ構成

`BLOGOS_ARCHITECTURE.md` 22章に従う（D-11-03）。ディレクトリとnamespaceは一致させる（PSR-4）。

## 5-2. Controllerの名前空間とView

（D-11-02）

| 名前空間 | 用途 | ルート名の先頭 | Viewのディレクトリ |
| --- | --- | --- | --- |
| `Controllers\WordPressApi` | API確認画面 | `wp-api.` | `wordpress-api/` |
| `Controllers\Database` | DB確認画面 | `database.` | `database/` |
| `Controllers\Api` | BlogOS自身のJSONエンドポイント | `api.` | ― |
| 機能ごと（例：`Controllers\Posts`） | 業務画面 | 機能名（例：`posts.`） | 機能名 |

## 5-3. ルート名とController

* ルート名はドット区切りで `機能.操作` とする（例：`posts.index`、`posts.show`、`drafts.update`、`wp-api.categories.show`、`database.categories.index`）（D-11-04）。
* Controllerは画面ごとではなくリソースごとに作り、`index` / `show` / `store` / `update` / `destroy` 等のメソッドで操作を分ける。
* ルートパラメータは、内部IDかWordPress IDかが分かる名前にする（例：DB確認画面・業務画面は `{post}`、API確認画面は `{wordpressId}`）。

## 5-4. クラス名

| 種類 | 例 |
| --- | --- |
| Model | `Blog`、`Post`、`Page`、`Category`、`Author`、`Media`、`ArticleDraft` |
| Repository | `BlogRepository`、`PostRepository` |
| Service | `PostService`、`SyncService` |
| DTO（WordPress API） | `PostApiDto`、`CategoryApiDto`、`AuthorApiDto` |
| API Client | `WordPressApiClient`、`OpenAiClient` |
| Enum | `ChangeSource`、`SyncTrigger`、`PushOperationState` |

`DataService`、`CommonService`、`UtilityService`、`Manager`、`Helper` など、何を担当するか分からない名前は使わない。

## 5-5. メソッド・変数

* メソッド名は動作を表す（`get`、`find`、`create`、`update`、`delete`、`sync`、`fetch` などを、クラスの責務に応じて具体化する）。
* Booleanは `is_` / `has_` などで意味が分かるようにする（例：`is_selected`、`has_error`）。
* 1つの変数に意味の異なるデータを繰り返し代入しない。
* 意味の分からない数値・文字列をコードに直接書かない。Config・定数・Enumを使う。

## 5-6. DBの列名

ID・参照・日時・本文の列名は `BLOGOS_DATABASE.md` 3章に従う。特に、`id` は常にBlogOS内部のIDであり、WordPress IDは `wordpress_id` 等に保存する（D-02-02）。

## 5-7. 列挙値

変更元・状態・種類などは、PHPのBacked Enum（文字列）で管理する。DBのenum型は使わない（D-02-07）。Enumの値は、DB設計書・WordPress APIの値との互換性を確認して定義する。

# 6. DBの実装

## 6-1. Migration

* Migrationは `BLOGOS_DATABASE.md` に基づいて作成する。「あった方が便利」という理由で、設計書にない列を追加しない。必要な場合は先にDB設計書を更新する。
* 外部キー・削除時の動作・UNIQUE・INDEX・CHECK制約は、DB設計書 11章に従う。
* 既存データがある状態で変更する場合は、NULL可否・Default・UNIQUE・外部キー・データ移行を確認する。
* 必要に応じてrollbackできるようにする。

## 6-2. DB変更時の確認範囲

DB要件 → DB設計書 → Migration → Model → Repository → Service → Controller → View → Test の依存関係を確認する。

## 6-3. 利用するDB

開発環境・テスト・XServerのいずれもMySQLを使う（D-12-05）。外部キー・CHECK制約・JSON・ロックの動作がDBの種類によって異なるため、SQLiteで代用しない。

## 6-4. トランザクション

* 複数のテーブルを更新する処理はトランザクションを使う（例：本体の更新＋関連の更新＋履歴の作成）。
* 外部APIとの通信をトランザクションの中で行わない。「API通信 → 結果の確認 → トランザクション → DB更新」の順とする。
* 同期のトランザクションは1レコード単位とする（ARCHITECTURE 13-4）。

## 6-5. クエリ

* N+1を避ける（eager loading、JOIN、まとめて取得）。
* 開発環境では `Model::preventLazyLoading()` を有効にし、遅延読み込みを検出する（D-11-01）。
* 必要な列だけを取得し、大量データに対して無条件に全列を取得しない。
* 大量データを画面に表示する場合はページネーションを使う。大量データの処理はchunk等で分割し、全件を一度にメモリへ読み込まない。
* SQLを文字列連結で組み立てない（Query Builder / Eloquentを使う）。

## 6-6. 冪等性

同期・Import・Jobは、同じ処理を複数回実行しても重複データや不整合が起きないようにする。WordPress由来のデータは `blog_id + wordpress_id`（または `blog_id + slug`）で既存を確認し、作成または更新する。

## 6-7. まとめての更新

大量データをまとめて作成・更新する場合も、履歴の記録（8章）との整合性を保つ。履歴を作らずに一括更新しない。

# 7. WordPress APIの実装

取得条件・差分の判定・反映の手順は `BLOGOS_WORDPRESS_API.md` に従う。本章は実装上のルールを定める。

## 7-1. 通信

* すべての通信にtimeoutを設定する。リトライは WORDPRESS_API 27〜28章の範囲に限る。
* ページネーションは `X-WP-TotalPages` を使って最後まで取得する。無制限の全件取得をしない。
* 通信の失敗を `[]` などに変換して正常終了させない。取得0件と取得失敗を区別する。

## 7-2. 日時

`date` / `date_gmt` / `modified` / `modified_gmt` を混同しない。比較・並べ替えにはGMTの値を使う（D-05-08）。日時による検索では、タイムゾーンと、範囲の端を含むかどうかを明確にする。

## 7-3. URL

表示用URL、ホームURL（`home`）、WordPressアドレス（`url`）、REST APIのURLを区別する。BlogOSの接続先は常に `home` を基準にする（D-13-01）。

## 7-4. JSON

JSONを扱う場合は、JSONとして保存するのか、配列として扱うのか、正規化するのかを明確にする。JSON列の使い方はDB設計書 3-10 に従う。

## 7-5. コメント

WordPress APIを扱う処理では、エンドポイント、パラメータを指定する理由、認証が必要な理由、特殊な処理の理由をコメントに書く。

# 8. 同期・反映・履歴の実装

## 8-1. 同期

* ブログ単位でロックし、同時に同じブログを同期しない（ARCHITECTURE 28章）。
* 同期の実行記録（`sync_runs` 等）を必ず作成・更新する。
* 失敗したリソースだけを再実行できるようにする。
* 通信の失敗だけを理由に、DBのデータを削除・論理削除しない（WORDPRESS_API 16-2）。
* 同期処理は、WordPress由来のテーブルだけを更新する。BlogOS独自のテーブルを変更しない（D-01-11）。

## 8-2. 反映

* 反映は必ず `wordpress_push_operations` を通し、状態を `pending → sent → wp_succeeded → completed` の順に進める。WordPressの応答は受信直後に最優先で保存する（ARCHITECTURE 13-5）。
* 反映直前の競合確認を省略しない（WORDPRESS_API 21章）。
* 反映に成功したら、送信した内容ではなくWordPressの返却値でDBを更新する。
* タイムアウトした反映をリトライしない。
* 公開・削除・WordPressの設定変更は、確認画面を挟む。削除操作では対象を明確に表示し、大量の削除・更新では対象件数と条件を確認させる。

## 8-3. 履歴

* 履歴の構造と変更元は `BLOGOS_DATABASE.md` 8章に従う。
* 履歴は、対象データの更新と同じトランザクションの中で記録する。
* 同時に起きた変更には同じ `change_set_id` を付ける。
* 差分がない場合は履歴を作らない。
* 変更元（`source`）と、関連する記録（`sync_run_id`、`wordpress_push_operation_id`、`user_id`）を必ず設定する。

---

# 9. 削除の実装

削除の扱いは `BLOGOS_DATABASE.md` 13章と `BLOGOS_WORDPRESS_API.md` 16章・22章に従う。実装では次を守る。

* WordPress側で削除されたデータは、Laravelの `SoftDeletes`（`deleted_at`）ではなく `wordpress_deleted_at` で扱う。
* WordPress由来のデータを、同期で物理削除しない。
* 削除処理では、論理削除か物理削除か、関連データをどうするか、履歴を残すか、WordPress側も削除するかを明確にする。

# 10. BlogOSのAI機能の実装

AI機能の段階・実行方式・記録は `BLOGOS_ARCHITECTURE.md` 18章に従う。

## 10-1. 実行方式

* 手動実行とAPI実行を、共通のインターフェース（AI Executor）と2つの実装で作る。呼び出し側は実行方式を意識しない（D-07-06）。
* 実行方式は実行モードごとに設定で切り替える。

## 10-2. テンプレート・モデル

* AI実行テンプレートと品質基準は `resources/` から読み込む（D-07-05）。指示文をコードに直接書かない。
* モデル名をコードに直接書かない。設定またはテンプレートで指定する。
* AIには、品質基準の全文ではなく必要な部分だけを渡す（費用を抑えるため）。

## 10-3. 記録

* AIの実行ごとに `ai_generations` を記録する。生成方法（実行方式・提供元・モデル・推論の深さ）とテンプレート・品質基準のバージョンを必ず設定する（D-07-07）。
* API実行では、応答に含まれる正確なモデル名を記録する。

## 10-4. 制限

* AIが書き込めるのは、評価結果と編集案だけとする。WordPress由来のテーブルを変更しない。WordPressへ直接アクセスしない（D-07-01）。
* 1回の指示につき実行は1回（設定値）とする。自動で繰り返さない（D-07-03）。
* 月の費用上限と1回あたりの上限を確認してからAPI実行する（D-07-08）。
* AIの出力を無条件に信用しない。出力の形式を検証してから保存する。
* 認証情報と、保存しないと決めた個人情報を、AIへの入力に含めない。

## 10-5. 品質基準との関係

品質基準（`resources/quality/`）は記事の品質の基準であり、本書（ソフトウェアの開発ルール）とは別物である。品質基準をコードの実装ルールとして扱わない。

# 11. Google APIの実装

* Google APIも外部APIとして扱い、Client・DTO・Service・Repositoryに分ける。
* 取得したデータとDBに保存するデータを分ける。
* 取得した期間・日時・タイムゾーンを明確に記録する。
* 記事との対応付けは `BLOGOS_DATABASE.md` 12-2 に従う。
* Google APIは、LaravelのHTTPクライアントで REST API を呼ぶ（`app/Clients/Google`）。Googleの公式ライブラリは使わない。テストでは `Http::fake` で偽の応答に置き換える（D-21-06）。
* 認証は OAuth に統一し、トークンは `google_accounts` に暗号化して保存する。トークンをログ・画面・例外のメッセージに出さない（D-21-01）。
* Google APIを呼ぶのは、毎日の取得・手動の取得・Google連携の設定画面（対応先の候補の読み込み）だけとする。分析の画面は保存済みのデータ（DB）から表示する。

# 12. エラー処理・ログ

## 12-1. エラーを握り潰さない

次のような処理は禁止する。

```php
try {
    // 処理
} catch (\Exception $e) {
    return [];
}
```

エラーを正常な空データとして扱うと、原因が分からなくなるためである。予期しないエラーは例外として扱う。

## 12-2. メッセージ

* 利用者には、理解しやすいメッセージを表示する（例：「接続に失敗しました。」）。
* ログには、例外、URL、HTTPステータス、エラーコード、スタックトレースなど調査に必要な情報を残す。
* 利用者にスタックトレースを表示しない。本番環境ではDebugを無効にする。

## 12-3. 外部APIのエラー

同期・反映でエラーになった場合は、応答本文を全文、`sync_issues` または `wordpress_push_operations` に保存する（D-10-03）。

## 12-4. ログに出力しないもの

パスワード、Application Password、APIキー・トークン、Cookie、セッション情報、Secret、個人情報、リクエストの `Authorization` ヘッダー。

大量のログを保存する場合は、容量を管理する。

# 13. セキュリティ

## 13-1. 認証と認可

* ログイン画面以外は、ログインを必須とする（D-03-01）。
* ログインの成功・失敗とログアウトを `login_histories` に記録する。パスワードは記録しない（D-17-03）。
* ログインの試行回数を制限する。同じメールアドレスとIPアドレスの組み合わせで5回失敗したら、1分間ログインを止める。止めた試行も記録する（D-17-06）。
* 利用者の認証情報（メールアドレス・パスワード）をSeeder等のソースコードに書かない。環境変数から読む（D-17-01）。
* テスト用・初期状態のユーザーを作成するSeederを、どの環境でも実行される場所に置かない（D-17-02）。
* 認証（誰か）と認可（何をしてよいか）を区別する。権限の確認が必要な処理は、Middleware・Policy・Gateを使う。

## 13-2. 認証情報

* WordPressの認証情報は `blog_credentials` に暗号化して保存する（D-03-02）。画面に再表示しない。
* WordPress側では、管理者のApplication Passwordを「BlogOS」という名前で専用に発行して使う。漏えいが疑われたら、そのパスワードだけを無効化する（D-03-04）。
* AIのAPIキーは .env で管理する。GoogleのOAuthトークンはDBに暗号化して保存する（D-03-05）。
* API確認画面では、`Authorization` ヘッダーと、機密性のあるクエリパラメータを伏せ字にする（D-03-03）。
* `APP_KEY` は、DBのバックアップとは別に保管する。変更する場合は `APP_PREVIOUS_KEYS` を使い、既存の暗号化データを復号できるようにする。
* テストデータに本番の認証情報を使わない。本番データを開発環境にコピーする場合は、個人情報・認証情報に注意する。

## 13-3. Web

* 状態を変更するフォームにはCSRF対策を行う。
* 表示はBladeの自動エスケープを基本とする。`{!! !!}` によるHTMLのそのままの出力は、WordPressの本文のようにHTMLとして表示する必要がある場合だけ使い、表示する場所と安全性を確認する。AIの出力も同様にXSSを考慮する。
* ファイルのアップロードでは、MIMEタイプ、拡張子、サイズ、ファイル名、保存先、アクセス制御を確認する。
* セッションに不要な機密情報を保存しない。
* BlogOSへのアクセスとWordPressとの通信はHTTPSを必須とする（D-03-06）。

# 14. 設定

* 環境によって変わる値は、Configと環境変数で管理する。
* アプリケーションコードから `env()` を直接呼ばず、Configを経由する。
* `.env` はGitにコミットしない。設定の見本は `.env.example` で管理し、実際の設定（`DB_CONNECTION=mysql` 等）と一致させる。
* ブログごとの値（WordPressの接続先・認証情報）はDBで管理し、`.env` に書かない（D-03-02）。
* HTTPS通信の証明書の検証を止めない（`verify => false` 等を使わない）。ローカルPCのウイルス対策ソフトが通信を検査する場合は、その証明書を加えた証明書ファイルを `HTTP_CA_BUNDLE` で指定する（D-18-06）。
* AIの実行方式・費用の上限などの設定値の保存先（config / DB）は未決定とする（D-13-09）。

# 15. 画面の実装

画面の種類は `BLOGOS_ARCHITECTURE.md` 6-3 に従う。

* **API確認画面**：見た目よりも、APIの情報を正確に確認できることを優先する。その場でAPIを呼び出して表示し、BlogOS独自の加工でAPIの情報を隠さない。JSONは整形し、コピーできるようにする。
* **DB確認画面**：列・値・関連・履歴・テーブルの状態を確認しやすくする。APIの生のJSONを一覧に表示することを目的にしない。
* API確認画面とDB確認画面の表示・Controller・Viewを混在させない。
* 一覧画面は複数データの比較、詳細画面は1件の詳細な確認を目的とする。
* 現在選択中のブログが常に分かるようにする。ブログが1件も登録されていない場合は、ブログ登録へ誘導する。
* フォームでは、Validation、CSRF、エラー表示、入力値の保持、成功メッセージを考慮する。処理後のRedirect先は、処理の流れに沿った画面にする。
* 並び順・絞り込み・検索は、DB・API・画面のどこで行うかを明確にし、処理はService・Repositoryに置く。
* UIを変更する場合でも、機能の仕様を勝手に変えない。

# 16. テスト

## 16-1. 基本

* 新しい機能を追加した場合は、可能な範囲でテストを追加する（Unit、Feature）。
* テストが失敗した場合は、失敗を無視して完了としない。どのテストが、なぜ失敗したか、修正済みか未解決かを報告する。
* テストは、要件を満たすこと、既存機能を壊さないこと、境界条件とエラーを適切に扱うことを確認する。

## 16-2. テスト用のDB

テストもMySQL（テスト専用のデータベース）で実行する。SQLiteのメモリDBで代用しない（6-3）。

## 16-3. 外部APIのテスト

* 本番のWordPress・Google・AIへ、テストで無制限にアクセスしない。Laravelの `Http::fake` 等を使う。
* 本番のWordPressに大量のテストデータを作成・削除しない。
* テスト用の固定レスポンスは、実際のWordPress APIのレスポンス構造に合わせる。
* WordPress API連携では、成功、401、403、404、429、5xx、タイムアウト、空の結果、不正なJSONを再現する。
* AIのレスポンスは固定化してテストできるようにする（手動実行の取り込みを含む）。

## 16-4. 重点的にテストするもの

* DB：作成・更新・関連・UNIQUE・外部キー・CHECK制約・履歴
* 同期：冪等性、差分の判定、削除判定の安全策、競合の記録、失敗したリソースだけの再実行
* 反映：反映記録の状態の進み方、競合確認、タイムアウト時の `unknown`、回復処理、二重反映の防止
* 選択中ブログの照合（別タブでの切り替え）
* 認証情報が画面・ログに出ないこと

## 16-5. Factory・Seed

* Factoryは、実際のDB設計と一致させる。
* Seedで、本番環境に意図しないテストデータを入れない。

# 17. Git・変更管理

## 17-1. コミット

* 変更前に `git status` で状態を確認する。
* 意味のある単位でコミットする。無関係な変更（例：カテゴリの修正、CSSの変更、AI機能の追加、DB変更）を1つのコミットにまとめない。
* コメントだけの修正、フォーマットだけの修正に、処理の変更を混ぜない。
* 既存ファイルの文字コード・改行コードを不用意に変えない。
* 変更後は `git diff` と変更ファイルの一覧で、意図しない変更がないことを確認する。

## 17-2. リファクタリング

* 目的（なぜ必要か、何が改善されるか、影響範囲）を明確にしてから行う。
* 動作の変更と構造の改善を、できる限り分ける。
* 「ついでに」無関係な変更をしない。
* ファイル全体を書き換える場合は、既存の機能をすべて維持していることを確認する。

## 17-3. 未使用コード・名前の変更・移動

* 未使用と思われるコード・ファイルも、すぐに削除しない。Route・Job等からの参照、将来機能か、外部からの利用を確認する。
* クラス・メソッド・ファイル名を変える場合は、すべての参照を確認する。
* ファイルを移動する場合は、namespace、use、Route、View、Test、configへの影響を確認する。

## 17-4. 依存ライブラリ

* 依存ライブラリはComposerで管理し、`composer.json` と `composer.lock` を一致させる。
* 更新時は、互換性のない変更、PHPのバージョン、Laravelとの互換性、テストを確認する。
* Laravel・PHPの更新は、通常の機能追加とは別の変更として扱う。

# 18. コメント・ドキュメント

## 18-1. コメント

* コメントは日本語で書く。クラス名・技術用語は英語表記のままとする（D-11-06）。
* コードを日本語にしただけのコメント（例：`// $idにIDを代入する`）を書かない。
* 「なぜ必要か」「なぜこの方式か」「なぜ例外的な処理をしているか」を書く。
* 複雑なService・Clientには、クラスの役割・特殊な制約・戻り値・例外が分かるDocBlockを付ける。
* 既存のコメントに設計意図が書かれている場合は、変更時に確認する。

## 18-2. TODO

TODOは「何をするか」「なぜ必要か」が分かる内容にする。設計変更が必要なTODOは、コードだけに残さず設計資料にも記録する。

## 18-3. 設計書の更新

* 仕様変更が発生した場合は、コードだけを変えて設計書を古いままにしない。
* 設計書を変更する場合は、決定を `BLOGOS_DECISIONS.md` に記録し（何が・なぜ変わったか）、設計書の冒頭のバージョンと最終更新日を更新する。
* 設計書同士の整合性を確認する。

# 19. 本番環境・リリース

* 本番環境への変更は、開発環境で検証してから行う。
* リリース前に、Migration、環境変数、Config、Route、API、DB、テスト、セキュリティを確認する。
* 本番のMigrationでは、バックアップ、Rollback、停止時間、データ移行、失敗時の復旧を確認する。
* XServerのcron（`schedule:run`、`queue:work`）の設定を確認する（ARCHITECTURE 28章）。
* 本番のWordPressへの作成・更新・削除・公開は慎重に扱う。本番の記事にAI処理を適用する場合は、対象記事・変更内容・公開状態を確認する。
* 重要なデータの変更では、変更前後を比較できるようにし、バックアップと復旧の方法を考慮する。
* 実験的なコード・プロトタイプを、そのまま本番の実装に持ち込まない。

# 20. 開発支援AIの利用

本章は、Claude Code等の**開発支援AI**を使って開発する場合のルールである（BlogOSに組み込む**BlogOSのAI機能**は10章。D-07-09）。Claude Code固有の作業手順は `CLAUDE.md` で定義する。

* 開発支援AIに設計判断を無条件に委ねない。調査・分析・差分の整理・実装案・コード生成・テストは任せてよい。
* 重要な設計変更、要件の変更、DB構造の変更、認証の変更、API設計の変更、削除・公開などの重大な操作は、人間が確認する。
* 大量のファイルを自動で修正する場合は、対象・変更内容・影響を事前に確認する。
* 開発支援AIに「現在のコードを基準に設計を決めさせる」状態にしない。理想設計と現在の実装を比較させる。
